# Регламент: вход и выход Savebit VPN

Что делать руками на серверах в типовых ситуациях. Общее устройство и установка описаны в [README](../README.md).
Здесь «вход» (мастер) — российский сервер, к которому подключаются друзья, «выход» (слейв) — зарубежный сервер,
через который трафик уходит в интернет.

```
Клиент (Happ) ──► Вход master-phoenix-vk ──► Выход slave-deutch-firstbyte ──► Интернет
                   VK Cloud, 89.208.87.102     firstbyte, 159.255.36.14
                         ▲   9443 (туннель к API)   │
                         │◄─────────────────────────┘
                         ▼
                   api.savebit.ru (Timeweb, 5.42.114.106)
```

Главное правило: **конфиг Xray руками не правим**. Всё, что меняется (друзья, порты, маскировка, версия Xray, доступ
к выходам, блокировки), меняется в админке `net.savebit.ru`, и агент сам применяет это в течение минуты.
На сервере остаются только агент, ключ и сеть.

## 1. Карта портов

Открыть в файрволе облака (в VK Cloud: «Виртуальные сети» → «Группы безопасности»). Значения по умолчанию,
в админке их можно поменять в настройках узла → «Дополнительно».

| Узел | Порт | Зачем | Откуда |
|---|---|---|---|
| вход | TCP 22 | SSH | свой IP |
| вход | TCP 443 | VLESS REALITY (основной профиль) | все |
| вход | TCP 8443 | VLESS XHTTP | все |
| вход | UDP 443 и UDP 20000–20050 | Hysteria2 и смена портов | все |
| вход | TCP 9443 | туннель к API для выходов | IP выходов (можно всем) |
| выход | TCP 22 | SSH | свой IP |
| выход | TCP 443 | канал вход → выход (REALITY/XHTTP) и прямой профиль | все |
| выход | UDP 443 | Hysteria2 вход → выход и прямой профиль | все |

Исходящие с узлов: в интернет без ограничений, вход должен видеть `api.savebit.ru:443` напрямую.
Если на сервере включён ufw, агент сам откроет в нём нужные порты; файрвол облака он не видит, его открываешь ты.

## 2. Быстрая проверка узла

В админке, «Узлы»: у карточки должен быть статус **онлайн**. Остальные статусы:

| Статус | Значит | Куда смотреть |
|---|---|---|
| ждёт установки | агент ни разу не выходил на связь | установи узел ([3](#3-новый-вход), [4](#4-новый-выход)) |
| нет связи | отчётов нет больше 5 минут | [раздел 5](#5-письмо--узел-не-отвечает) |
| ошибка | агент на связи, но последний конфиг не применился | [раздел 6](#6-узел-ошибка-в-админке) |
| применяет конфиг | новая ревизия ещё не дошла (обычно до минуты) | подождать или `savebit-agent sync` |

На сервере:

```bash
sudo savebit-agent status
```

Здоровый узел выглядит так: `Xray: …, служба работает`, `Агент: служба работает`, `Синхронизация:` меньше минуты назад,
`Ошибка: нет`. У выхода, который ходит через туннель, в строке API стоит `(через АДРЕС_ВХОДА:9443)`, а у **входа такой
пометки быть не должно** (см. [13](#13-чего-не-делать)).

## 3. Новый вход

1. Арендуй сервер в России (Ubuntu 22.04+, 1 vCPU / 1 ГБ хватает на десяток друзей). Открой порты из [раздела 1](#1-карта-портов).
2. Перед установкой проверь, что IP не режут мобильные операторы ([раздел 8, шаг 1](#шаг-1-проверить-адрес)). Тест занимает
   пять минут, а грязный адрес потом стоит вечера разборов.
3. Админка → «Узлы» → «Добавить узел» → роль **Вход**. Имя латиницей (оно видно друзьям в Happ), адрес — публичный IP.
   Скопируй ключ (показывается один раз).
4. На сервере:
   ```bash
   curl -fsSL https://raw.githubusercontent.com/knyazevi81/strangling-hand-deploy/main/deploy-entry.sh | sudo bash
   ```
5. `sudo savebit-agent status` и карточка в админке «онлайн». Выходы подтянутся сами: вход строит к ним канал по
   данным из API, на выходах ничего делать не нужно.
6. Друзьям: обновить подписку в Happ, в ней появятся профили нового входа.

Маскировка REALITY по умолчанию `max.ru`: российский сайт из белых списков, который открывается из дата-центров.
Если хостинг не видит `max.ru:443` (`curl -sI https://max.ru` с сервера), поменяй «Сайт для маскировки» и SNI в настройках
узла на другой российский сайт, доступный с этого сервера.

## 4. Новый выход

1. Сервер за границей, порты из [раздела 1](#1-карта-портов). Если там был x-ui, 3x-ui, Marzban или старый Xray, удали их
   или хотя бы останови: они держат порт 443.
   ```bash
   ss -tlnup | grep -E ':443\b'
   ```
2. Админка → «Добавить узел» → роль **Выход**, адрес — публичный IP, страна. Скопируй ключ.
3. Проверь, видит ли сервер API:
   ```bash
   curl -s -m 8 -o /dev/null -w 'api: %{http_code}\n' https://api.savebit.ru/
   ```
   - любой код, кроме `000`: ставь обычным способом:
     ```bash
     curl -fsSL https://raw.githubusercontent.com/knyazevi81/strangling-hand-deploy/main/deploy-exit.sh | sudo bash
     ```
   - `000`: ставь через туннель на входе:
     ```bash
     curl -fsSL https://raw.githubusercontent.com/knyazevi81/strangling-hand-deploy/main/deploy-exit.sh \
       | sudo bash -s -- --key sbn_КЛЮЧ --via 89.208.87.102:9443 --yes
     ```
4. Через минуту входы сами добавят новый выход в балансировщик (leastPing). Если выход нужен не всем, настрой
   «Кто может пользоваться» в карточке выхода.

## 5. Письмо «🔴 узел не отвечает»

Письмо приходит, когда от агента нет отчётов дольше 5 минут, и ещё одно, «🟢 снова работает», когда он вернётся.
Если пропал **выход**, друзья обычно ничего не замечают: вход переводит трафик на другие выходы. Если пропал
**единственный вход**, у всех не работает VPN.

По шагам:

1. **Жив ли сервер.** `ssh` на него. Не пускает: панель хостинга (сервер выключен, кончились деньги, сеть), перезагрузи
   оттуда. Службы стартуют сами.
2. **Живы ли службы.**
   ```bash
   sudo savebit-agent status
   systemctl status savebit-agent savebit-xray --no-pager
   ```
   Служба упала: `sudo systemctl restart savebit-agent savebit-xray` и `journalctl -u savebit-agent -n 50`.
3. **Видит ли узел API.**
   ```bash
   sudo savebit-agent check
   ```
   - выводит JSON с именем узла: связь есть, через минуту статус станет «онлайн»;
   - «API не принял ключ»: ключ перевыпустили, см. [раздел 10](#10-ключ-узла-утёк);
   - «API недоступен»: если это выход, переведи его на туннель ([раздел 7](#7-выход-не-видит-apisavebitru)); если вход
     или туннель не помогает, проверь сам API: `curl -I https://api.savebit.ru/` с любого компьютера.
4. **Лежит API** (не отвечает отовсюду). Узлы при этом **продолжают работать** на последнем конфиге, друзья ничего не
   замечают, нельзя только менять настройки. Чини бэкенд на 5.42.114.106; агенты сами догонят изменения.
5. **Выход ходил через вход, а вход сменил IP или лежит.** На выходе `sudo savebit-agent set-via НОВЫЙ_ВХОД:9443`.

## 6. Узел «ошибка» в админке

Текст ошибки есть в карточке и в `sudo savebit-agent status`. Узел в это время работает **на прошлом рабочем конфиге**.

| Ошибка | Причина | Что делать |
|---|---|---|
| `конфиг не прошёл проверку xray -test` | неудачные настройки узла в админке или баг бэкенда | верни прежние значения в «Дополнительно»; если не помогло, это баг бэкенда (текст ошибки ему в issue) |
| `Xray не запустился с новым конфигом, вернул прежний` | порт занят другой программой | `ss -tlnup \| grep -E ':(443\|8443\|9443)\b'`, останови чужую службу |
| `permission denied` на `access.log` | агент старше 0.2.1 | `sudo savebit-agent update` |
| ошибка скачивания Xray | сервер не видит GitHub | проверь `curl -I https://github.com`; временно поможет только сеть хостинга |

После исправления: `sudo savebit-agent sync`, статус должен стать «онлайн».

## 7. Выход не видит api.savebit.ru

Хостинги иногда режут друг друга (firstbyte → Timeweb). Решение: выход ходит в API через вход, порт 9443.
Подробно, с проверками, в [README](../README.md#сервер-не-видит-apisavebitru). Коротко, **на выходе**:

```bash
sudo savebit-agent set-via 89.208.87.102:9443
sudo savebit-agent check
```

Обратно напрямую: `sudo savebit-agent set-via off`. Туннель проверяет сертификат `api.savebit.ru` насквозь, вход трафик
не видит и подменить не может.

## 8. Оператор режет вход: смена IP входа

Признаки: у друзей на одном операторе (чаще мобильном: Билайн, МТС) VPN «подключается, пинг есть, а сайты не грузятся»,
при этом через Wi-Fi или другого оператора всё работает. Так выглядит «заморозка» ТСПУ: соединение не рвётся, пакеты
просто перестают доходить. Обычно это решение по IP входа, и протокол, SNI и fingerprint тогда не помогают.

### Шаг 1. Проверить адрес

На входе (или на сервере с IP-кандидатом) запусти тестовый сервер. Открой в файрволе облака TCP 8444:

```bash
curl -fsSL https://raw.githubusercontent.com/knyazevi81/strangling-hand-deploy/main/tools/tls_probe.py \
  | sudo python3 - --port 8444 --minutes 15
```

С телефона **без VPN, через проблемного оператора** открой `https://IP:8444`, пропусти предупреждение о сертификате,
подожди до 30 секунд. В выводе (и в `/tmp/tls_probe.log`):

| Строки для IP телефона | Вывод |
|---|---|
| `TLS ok` и `OK 2MB sent` | адрес для этого оператора чистый, ищи причину в клиенте ([раздел 9](#9-друг-подключается-но-не-работает)) |
| `TLS FAILED: … timed out` | оператор режет TLS к этому IP: нужен новый адрес |
| `FROZEN after ~16 KB` | классическая заморозка: нужен новый адрес |
| ничего нет | TCP не дошёл: проверь порт 8444 в файрволе или проверяемая сеть режет IP целиком |

Строки `CERTIFICATE_UNKNOWN` до нажатия «Продолжить» — это браузер отказывается от самоподписанного сертификата, так и должно быть.

### Шаг 2. Получить новый IP (VK Cloud)

Квота на плавающие IP обычно 1–2 адреса, поэтому сначала освободи место:
«Виртуальные сети» → «Плавающие IP» → у старого адреса «Отвязать», затем «Удалить». Потом «Добавить» и «Привязать»
к той же ВМ (к её порту в сети). Группа безопасности остаётся та же. Учти: удалённый адрес обратно не вернуть.

Если квоты хватает на два адреса, надёжнее сначала привязать новый, проверить его (шаг 1) и только потом удалять старый.

### Шаг 3. Проверить новый адрес

Шаг 1 на новом IP. Если и он `TLS FAILED`, оператор режет всю подсеть облака: бери ещё один адрес, а если опять
грязный, ставь вход у другого провайдера ([раздел 3](#3-новый-вход)).

### Шаг 4. Переключить

1. Админка → «Узлы» → вход → «Изменить» → **Адрес** = новый IP → сохранить. Конфиг входа от этого не меняется (Xray
   слушает все адреса), меняются подписка и адрес, по которому ходят выходы.
2. **На каждом выходе**, который ходит через туннель:
   ```bash
   sudo savebit-agent set-via НОВЫЙ_IP:9443
   sudo savebit-agent check
   ```
   На **входе** `set-via` не трогать, он ходит в API напрямую.
3. Остановить тестовый сервер: `Ctrl+C` в его окне (или подожди, пока он сам выйдет по таймеру).
4. Друзьям: Happ → обновить подписку (↻), адрес подставится новый. В v2rayNG и других клиентах с вручную вставленными
   ключами удалить старые профили и скопировать ключи заново со страницы VPN на `net.savebit.ru`.
5. Проверка: телефон через проблемного оператора, VPN включён, тяжёлая страница или speedtest.

## 9. Друг: «подключается, но не работает»

Иди сверху вниз, первый подходящий пункт обычно и есть ответ.

1. **Статус на сайте.** У друга на `net.savebit.ru` → VPN — табло узлов. Что-то красное: [раздел 5](#5-письмо--узел-не-отвечает).
   Кнопка «У меня не работает» присылает тебе письмо: сеть (Wi-Fi или мобильный), оператор, профиль, комментарий и снимок статуса узлов.
2. **Не заблокирован ли он** и есть ли у него доступ к выходам (админка → пользователь: отметка блокировки и вкладка «Доступ»). Во вкладке «IP» видно, с каких адресов и операторов он подключался.
3. **Подписка свежая?** Пусть обновит подписку в Happ. После смены IP входа старые профили не работают.
4. **Сеть.** Работает через Wi-Fi, но не через мобильный (или наоборот): проверь адрес по [разделу 8](#шаг-1-проверить-адрес)
   прямо с его телефона.
5. **Профиль.** Пусть попробует все три профиля входа: REALITY, XHTTP, Hysteria2. Если работает только какой-то один,
   оператор режет конкретный протокол, пусть пользуется рабочим.
6. **Клиент.** Нормально работают Happ (iOS, Android, macOS, Windows) и v2rayNG: у них то же ядро Xray, что у
   серверов. С остальными бывают проблемы:
   - Hiddify и другие клиенты на sing-box не умеют XHTTP, а Xray-JSON из v2rayNG понимают плохо. TLS Tricks и
     мультиплекс в них ломают REALITY с Vision;
   - **не запускать клиент через `sudo`** (macOS, Linux): он настроит прокси и VPN для root, подключится и отвалится,
     а потом ещё и перестанет запускаться от обычного пользователя. Лечится выходом из всех копий, сбросом его
     настроек и перезагрузкой;
   - два VPN-клиента одновременно мешают друг другу (macOS: «Системные настройки» → «VPN и фильтры»; там же
     проверь, что у клиента есть разрешение на сетевое расширение);
   - на macOS остаток системного прокси после падения клиента: «Сеть» → Wi-Fi → «Подробнее» → «Прокси», всё выключить.
7. **Разбор на сервере.** Узнай внешний IP друга (он открывает `ifconfig.me` без VPN), на входе:
   ```bash
   curl -fsSL https://raw.githubusercontent.com/knyazevi81/strangling-hand-deploy/main/tools/capture.sh -o /tmp/capture.sh
   sudo bash /tmp/capture.sh start IP_ДРУГА 300
   ```
   Пусть друг включит VPN и откроет пару сайтов. Если с того же устройства ты сидишь в SSH, сессия порвётся, это нормально:
   запись идёт в фоне. Потом `sudo bash /tmp/capture.sh report`:

   | Что в отчёте | Значит | Что делать |
   |---|---|---|
   | соединений нет | клиент не доходит до сервера | IP и порт в профиле, разрешение VPN на устройстве, режим клиента |
   | рукопожатия по ~6 КБ к клиенту, дальше клиент молчит, «принятых соединений» нет или единицы | клиенту не нравится рукопожатие | клиент или его настройки (пункт 6), время на устройстве |
   | `accepted … email:` есть, но только к нескольким адресам | туннель работает, не работают DNS или маршруты в клиенте | DNS в клиенте (`https://1.1.1.1/dns-query`), правила маршрутизации |
   | к клиенту уходит ~16 КБ, потом повторы без ответа | заморозка оператором | [раздел 8](#8-оператор-режет-вход-смена-ip-входа) |
   | только UDP, `accepted` нет | Hysteria2 не проходит | REALITY или XHTTP; проверь UDP 443 в файрволе облака |

   Для `accepted`-строк нужен включённый сбор данных (админка → «IP и домены» → «Сбор данных: IP и домены»).
   Другие устройства друга в той же сети выходят в интернет с того же IP. Если на них тоже включён VPN, записи
   перемешаются, так что на время теста VPN на них лучше выключить.

## 10. Ключ узла утёк

Ключ даёт доступ только к конфигу своего узла, но в конфиге есть ключи друзей. Поэтому если ключ засветился
(в чате, на скриншоте, в публичном репозитории):

1. Админка → карточка узла → ⋮ → **«Новый ключ»**. Старый перестаёт работать сразу, узел продолжает работать
   на последнем конфиге.
2. На сервере:
   ```bash
   sudo savebit-agent rekey sbn_НОВЫЙ_КЛЮЧ
   sudo savebit-agent status
   ```
   `rekey` сначала проверяет новый ключ через API (с учётом `via`) и только потом сохраняет его.

Если засветился **личный ключ друга** (ссылка `vless://…`), он нажимает «Сбросить ключи» на странице VPN и обновляет
подписку на всех своих устройствах.

## 11. Обновления: агент и Xray

- **Xray** обновлять руками не нужно: версию задаёт API, агент скачивает её с GitHub, проверяет контрольную сумму, тестирует
  конфиг и при неудаче откатывается. Хранятся 3 последние версии.
- **Агент**, после изменений в этом репозитории:
  ```bash
  sudo savebit-agent update
  savebit-agent version
  ```
  Ключ, конфиг и Xray при этом не трогаются. Обновляй сначала один выход, потом остальные, вход в последнюю очередь.
- **Система.** `apt upgrade` и перезагрузка безопасны, службы стартуют сами. Перезагрузку входа лучше делать ночью:
  на минуту у друзей пропадёт VPN.

## 12. Перезагрузка, переезд, удаление узла

- **Перезагрузка** сервера: ничего делать не нужно. После неё `sudo savebit-agent status`.
- **Переезд на другой сервер**, вход или выход:
  1. на новом сервере установка с ключом старого узла (или «Новый ключ» и установка с ним);
  2. в админке поменять адрес узла;
  3. для входа: `set-via` на выходах ([8, шаг 4](#шаг-4-переключить)) и обновление подписки у друзей;
  4. на старом сервере удаление (ниже).

  Сертификат Hysteria2 на новом сервере будет другим: подписка подхватит его сама, друзьям достаточно обновить её.
- **Удаление:**
  ```bash
  curl -fsSL https://raw.githubusercontent.com/knyazevi81/strangling-hand-deploy/main/install.sh \
    | sudo bash -s -- --uninstall --purge
  ```
  и удалить узел в админке. Порты в ufw и в файрволе облака закрой сам.

## 13. Чего не делать

- **Не включать `set-via` на входе.** Вход тогда ходит в API через собственный Xray: пока Xray работает, всё нормально,
  но стоит ему упасть или получить плохой конфиг, агент не сможет скачать исправление. Если в `status` входа
  стоит «(через …)», выполни `sudo savebit-agent set-via off`.
- **Не править `/etc/savebit/xray/config.json` руками.** Агент перезапишет его при следующей ревизии. Нужные
  настройки задаются в админке.
- **Не ставить рядом x-ui и другие панели.** Они займут 443 и сломают применение конфига.
- **Не проверять «заблокирован ли IP» открытием `https://IP` в браузере.** Без SNI REALITY не отвечает так, как
  обычный сайт, и тест ничего не показывает. Для этого есть `tools/tls_probe.py`.
- **Не запускать VPN-клиенты через `sudo`** ([9, пункт 6](#9-друг-подключается-но-не-работает)).
- **Не отправлять ключи узлов в чаты.** Если отправил, [раздел 10](#10-ключ-узла-утёк).

## 14. Шпаргалка

| Задача | Команда |
|---|---|
| состояние узла | `sudo savebit-agent status` |
| синхронизироваться сейчас | `sudo savebit-agent sync` |
| проверить ключ и связь с API | `sudo savebit-agent check` |
| новый ключ | `sudo savebit-agent rekey sbn_…` |
| выход в API через вход / напрямую | `sudo savebit-agent set-via ВХОД:9443` / `off` |
| сменить адрес API | `sudo savebit-agent set-api api.savebit.ru` |
| обновить агента | `sudo savebit-agent update` |
| журнал агента / Xray | `journalctl -u savebit-agent -f` / `journalctl -u savebit-xray -f` |
| перезапуск служб | `sudo systemctl restart savebit-agent savebit-xray` |
| кто держит порт | `ss -tlnup \| grep -E ':(443\|8443\|9443)\b'` |
| видит ли сервер API | `curl -s -m 8 -o /dev/null -w '%{http_code}\n' https://api.savebit.ru/` |
| режет ли оператор IP | `curl -fsSL …/tools/tls_probe.py \| sudo python3 - --port 8444` |
| запись трафика клиента | `sudo bash /tmp/capture.sh start IP 300`, потом `report` |
| журнал соединений | `tail -f /var/lib/savebit/xray-log/access.log` |
